# changes：按版本归档的需求、设计和方案

每个版本一个子目录，放这个版本从需求到开发所需的全部文档。看某个版本做了什么、为什么这样做，只需要看它自己的目录。

## 目录结构

```
changes/
  v0.3/
    prd.md           需求：做什么、为什么做、不做什么、验收标准
    design/          设计稿：index.html 是设计稿本体，shots/ 是各画板截图
    spec.md          功能规格：把需求和设计稿落成逐条可测试的行为规则
    tech-design.md   技术方案：怎么实现、改哪些模块、数据怎么存、有什么风险
    release-notes-0.3.0.md   更新说明：发布时写，全文就是 GitHub 发布页的正文，应用内「查看更新说明」也读它
  v0.4/
    ...
```

## 四份文档各管什么

| 文档 | 回答的问题 | 什么时候写 | 谁确认 |
| --- | --- | --- | --- |
| prd.md | 做什么、为什么、做到什么程度算完成 | 版本开始时 | 项目负责人 |
| design/ | 界面长什么样、怎么交互 | PRD 确认后 | 项目负责人 |
| spec.md | 每个功能在每种情况下的准确行为（含边界情况和文案） | 设计稿确认后 | 产品自查，有疑问再问负责人 |
| tech-design.md | 代码怎么改、风险怎么防 | 设计稿确认后、开发前 | 产品和开发评审 |

## 流程

1. 写 prd.md，负责人确认。
2. 出 design/，负责人确认。
3. 写 spec.md 和 tech-design.md。
4. 开发，按 spec.md 和 prd.md 的验收标准逐条验收。
5. 写更新说明（格式固定，见下），负责人同意后发布。
6. 发布后，版本目录不再修改（补丁版本的更新说明除外）；后续改动写进下一个版本的目录。

## 更新说明的固定格式

从 v0.3 起，应用会读取 GitHub 发布页的正文，在「查看更新说明」里显示给用户，所以更新说明必须按固定格式写：

- 文件：`changes/v<主.次>/release-notes-<完整版本号>.md`，从 `changes/release-notes-template.md` 复制开始。
- 三个段落，顺序固定：`## 中文`、`## English`、`## 安装 / Install`。应用按界面语言只显示中文段或英文段，安装段只在 GitHub 页面显示。
- 中文段和英文段用「新功能 / 改进 / 修复 / 升级须知」分组，两种语言的条目一一对应。
- 发布前运行 `scripts/check-release-notes.sh <版本号>` 检查格式。

v0.2.0 和 v0.2.1 的更新说明在建立这个约定之前写成，仍在 `dist/RELEASE_NOTES.md`。

## 约定

- 文档用中文。
- 一个版本的范围变了，先改 prd.md，再改其他文档，保持一致。
- 设计稿里用到的照片引用仓库里 `design/photos` 的公开授权素材，不复制、不使用个人照片。
- v0.1 和 v0.2 的文档在建立本目录之前完成，仍在原位置：`prd.html` 和 `design/yilan-design.html`。
