# 一览的更新说明和发布

发布（push、打 tag、建 GitHub Release）必须等负责人明确同意。没有同意时只做到「更新说明写好、检查通过、发布包构建好」。

## 更新说明放在哪里

`changes/v<主版本.次版本>/release-notes-<完整版本号>.md`，例如 `changes/v0.3/release-notes-0.3.0.md`；补丁版本 0.3.1 也放在 `changes/v0.3/` 里。这份文件的全文就是 GitHub Release 的正文，不要在 GitHub 网页上另写一份。

从 `changes/release-notes-template.md` 复制开始写。

## 固定格式（应用依赖它）

三个一级段落，名字和顺序都不能改：

1. `## 中文`：界面语言是中文时，应用内只显示这一段。
2. `## English`：界面语言是英文时，应用内只显示这一段。
3. `## 安装 / Install`：系统要求、首次打开、SHA-256。应用内不显示，只在 GitHub 页面上看到。

中文段和英文段里用小标题分组，没有内容的小标题整个删掉：

| 中文 | English | 放什么 |
| --- | --- | --- |
| 新功能 | New | 以前做不到、现在能做到的事 |
| 改进 | Improved | 原有功能变得更好 |
| 修复 | Fixed | 问题修复 |
| 升级须知 | Upgrade notes | 升级后用户需要知道或做的事，例如快捷键变了 |

## 写法

- 每条以加粗的短名字开头，后面写用户看到的变化：`- **评星**：按 1 到 5 给照片打星，按 0 清除。`
- 站在用户角度写。不写内部名词（模块名、分支名、重构），不写用户感觉不到的改动。
- 修复类先写用户当时看到的现象，再写现在怎样。
- 中文段和英文段的小标题数量、条目数量、顺序必须一一对应。
- 只用这些格式：三级标题、无序列表、加粗、行内代码、链接。不用图片、表格、HTML、一级标题（应用内的显示只支持简单格式）。
- 内容来源：`changes/<版本>/prd.md` 的功能清单和这个版本的提交记录。PRD 里「尽量做」但最后没做的，不要写进去。

## 步骤

1. 确认版本号：`app/project.yml` 的 `MARKETING_VERSION` 和 `CURRENT_PROJECT_VERSION`。
2. 写更新说明，SHA-256 先留模板里的占位。
3. 负责人同意发布后，运行 `scripts/release.sh`，把它输出的 SHA-256 填进更新说明。
4. 运行 `scripts/check-release-notes.sh <完整版本号>`，必须通过。
5. 把更新说明给负责人看一遍，再发布。GitHub Release 的标题写「一览 Yilan v<版本号>」，正文用这份文件，不勾选预发布（预发布不会触发应用内的更新提醒）。
6. 发布后把 `changes/README.md` 状态表里这个版本标成已发布。
