# 写一览的功能规格（spec）

前提：`prd.md` 和 `design/` 都已确认。输入是这两份文档，不要在 spec 里悄悄改范围；发现 PRD 有缺口，先回头问负责人、改 PRD。流程见 `changes/README.md`。

## 格式

- 一行一条规则，带编号，编号格式「<模块>-<序号>」，例如 `R1-03`。
- 每条规则都标出它对应的 PRD 功能编号（例如「依据 R1」）。没有 PRD 依据的规则不要写；有 PRD 项没有任何规则，要补上。
- 一条规则只写一个行为，写成可以直接拿来测试的句子：在什么条件下，做什么操作，应该看到什么结果。
- 全文简体中文。

## 必须覆盖

- **状态**：每个界面元素在各种状态下的样子（默认、悬停、按下、禁用、无数据、加载中、出错）。
- **边界情况**：空文件夹、只有一个文件、文件无法读取、只读位置、磁盘满、超大文件、文件名重复、各种文件类型（图片、RAW、视频、GIF、SVG）。
- **文案**：每一处界面文字都写出完整的简体中文和英文两个版本，逐字照写，包括提示、菜单项、按钮、错误信息。对应的字符串放在 `app/Yilan/Resources/Localizable.xcstrings`。
- **快捷键**：每个快捷键写出按键、生效条件、和已有快捷键冲突时的处理。
- **用户文件**：任何会写、改、移动、删除用户文件的行为，要写清楚什么时候发生、失败时怎么办、能不能撤销。

## 写完之后

- 末尾加一张追溯表：PRD 编号对应的规则编号，方便核对没有遗漏。
- 更新 `changes/README.md` 状态表的 spec 一列。
- 规格由产品自查，有疑问再问负责人；与 `yilan-tech-design` 同时进行也可以，但两份文档互相不能矛盾。
