# 写一览的 PRD

先读 `changes/README.md`（流程和状态表）和 `AGENTS.md`。参照已确认的 `changes/v0.3/prd.md`、`changes/v0.4/prd.md` 的写法。PRD 由项目负责人确认，确认前不要开始设计。

## 文件位置和语言

- 文件：`changes/<版本号>/prd.md`。
- 全文简体中文，面向只读中文的负责人。英文术语第一次出现时用括号讲清楚，例如「RAW（相机原始格式照片）」「Lightroom（Adobe 的专业修图软件）」。
- 用大白话，写用户要什么，不写实现方法。

## 章节（按 v0.3、v0.4 的做法）

1. 标题「一览 v<版本> 需求文档（PRD）：<主题>」，下一行写状态和日期，例如「状态：已确认（日期）」。
2. 背景（用户反馈原文、现状）。
3. 目标与不做的事，两个列表。
4. 使用场景，写成小故事加步骤。
5. 功能需求：功能清单表，列为「编号 | 功能 | 说明 | 优先级」。需要时再加快捷键变化、数据存放、保存规则等小节。
6. 验收标准。
7. 已确认的决定（表格）和风险；v0.4 没有的章节可省，但涉及用户文件的版本必须写风险。

## 编号和优先级

- 功能编号要稳定，设计稿、spec、测试都用它追溯。已有编号不要改、不要复用。
- 优先级只有三档：**必须做**（不做就不发版）、**尽量做**（时间够就做）、**以后再议**（这版不做，记下来）。
- 每个版本都要有「不做的事」，明确挡住范围膨胀。

## 验收标准

- 用复选框 `- [ ]`，每条一个可以判断「做到了没有」的事实，带具体数字或现象（例如「0.1 秒内点亮」「原图修改时间不变」）。
- 每个必须做的功能至少有一条验收；涉及改写用户文件的，必须有「原文件没被损坏」的验收。
- 测试素材只用公开授权的图片和视频，不用个人照片。

## 写完之后

- 更新 `changes/README.md` 末尾的「版本状态」表（prd 一列：未开始 / 修改中 / 已确认）。
- 范围有变化时先改 PRD，再通知其他文档同步。
- 只提交 PRD 和状态表，等负责人确认后才进入 `yilan-design`。
