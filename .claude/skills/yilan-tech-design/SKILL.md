# 写一览的技术方案

前提：`prd.md` 和 `design/` 已确认。流程见 `changes/README.md`。写之前先读相关源码：代码在 `app/Yilan/`（App、Imaging、Model、Stage、Views、Resources），测试在 `app/YilanTests/`，工程配置在 `app/project.yml`。写的是代码里真实存在的类型和文件名，不要凭印象。

## 章节

1. **目标和范围**：一句话，并指出对应 PRD 的哪些编号。
2. **影响的模块和文件**：列出要新增或修改的文件，每个写一句改什么；用现有的结构，不要无谓重构。
3. **数据和文件格式决定**：数据存在哪里、什么格式、为什么这样选；有哪些方案被否决、理由是什么。
4. **对用户文件的风险和防护**：一览要读取用户的照片，凡是会写、改、移动、删除用户文件的地方，逐项写：最坏会发生什么、怎么防（例如先写临时文件再替换、默认另存副本、进废纸篓而不是直接删除）、怎么用测试证明。
5. **性能**：对「打开大文件夹」「连续切图」等路径有没有影响，怎么保证不变慢；PRD 里有流畅度验收的要写测量方法。
6. **测试计划**：每条 PRD 验收对应什么测试（自动测试放在 `app/YilanTests/`，不能自动化的写手动步骤）；测试素材只用公开授权的文件，并登记到 `app/Fixtures/CREDITS.md`。
7. **开发前必须先用实验验证的事**：凡是「应该可以」「行业惯例」这类没有实测过的假设，列出来，写明怎么验证、验证失败时的退路。这些实验要在正式编码之前做完，并把结果补写进这份文档。
8. **本地化和沙盒**：新增文案要进 `Localizable.xcstrings`（中英文）；目前 `project.yml` 里关闭了 App Sandbox，新增读写文件的实现要集中在一处，方便以后调整。

## 写完之后

- 更新 `changes/README.md` 状态表的 tech-design 一列。
- 发现 PRD 或 spec 不可行，先回头改它们，不要在方案里绕过去。
- 方案评审通过后才开始 `yilan-dev`。
